## Goal

Expose read-only reading exposure records on the capture surface, so a client can answer "what has
this learner read or been shown" without inventing a write path or reading mastery.

## What changed

- `app/worker/src/data/reads.ts`
  - registers a `reading` read operation with `concept_id`, `realm`, `limit` and `cursor`.
  - returns exposure rows joined to their concept, newest first (`occurred_at DESC, seq DESC`),
    with `id, concept_id, title, realm, level, occurred_at, accepted_at, local_day, source_json,
    content`. Paginated with the existing `page`/`paged` helper, so the 1–100 limit and cursor
    rules match every other read.
- `app/worker/src/mcp/server.ts`
  - `reading` is advertised on both the capture surface (`captureReadTools`) and the full surface
    (`readTools`, which stays a superset), with a read-only, non-destructive annotation and a
    description that states exposure is never assessed evidence.
- `app/worker/src/mcp/protocol.ts`
  - the served capture protocol's read notes describe `reading`, its filters and the
    withdrawn-record rule; the full protocol names it while orienting.
- `app/worker/test/capture-surface.test.ts`
  - the capture tool listing asserts `reading` is present.
  - a new test records exposure against two concepts in two realms, logs an inquiry, and proves:
    unfiltered listing returns both exposures; `concept_id` returns one; `realm` returns one; both
    filters together return none; the inquiry is not listed; after `retract` the withdrawn exposure
    disappears while the other remains. The full-mode test asserts `reading` is advertised there too.

## Decisions

- **`kind='exposure'`, not `strength='exposure'`.** `log_inquiry` also writes `strength='exposure'`,
  but an inquiry is a question, not something the learner read. Reading means exposure records only.
- **Withdrawn exposures are suppressed, not deleted.** A retraction appends a `record_corrections`
  row with `action='retract'` and leaves the evidence row in place, so `reading` joins through
  `record_corrections` with `NOT EXISTS`, mirroring how `inbox` suppresses retracted inquiries.
- **Both filters are conjunctive.** `concept_id` and `realm` may be sent together; a mismatch
  returns an empty page rather than being silently ignored.
- **Concept identity is carried on the row.** `title` and `realm` come from a join, so listing does
  not require a `concept_get` per record; `concept_id` keeps the exact stored identity, including a
  concept later merged elsewhere (no canonical redirect on historical exposure).
- **No migration and no write path.** `reading` is a pure projection over `evidence` +
  `concepts` + `record_corrections`; it cannot change mastery, scheduling or receipts.

## Known limits (attempt #a1)

- **Not deployed.** The hosted Worker still runs the previous capture release until the operator
  regenerates the approval and deploys. Live-endpoint listing is therefore tested on the handler
  surface, not observed against `https://teach-mcp.hritvikdinkar.workers.dev`.
- **Evidence file is not on the branch.** The task's declared write paths list only the four code
  and test files, so the coordination pre-commit guard refuses a commit that stages
  `evidence/W-7.md`. This file sits in the work home the review request is sent from but is not part
  of `76ce520`. The write paths should include the evidence path next time.
- **Ordering ties.** Two exposures with the same `occurred_at` fall back to `seq DESC`, which is
  total but not identical to creation order for backdated `occurred_at` values.
- **No cursor stability across writes.** Like other paged reads, the cursor is a base64 offset over
  the result set; a write between pages can shift a row across the boundary. This matches the
  existing read contract and was not widened here.
- **Archived and merged concepts still appear.** Historical reading is a record of what happened;
  `reading` does not hide exposure for an archived or merged concept. Filtering by `realm` uses the
  joined concept's realm, as stored.
